# Database Structure Rules

## Purpose

This document defines the rules to preserve when changing the database
structure, ORM models, SQL repositories, schema initialization or Alembic
migrations.

## Schema Contract

- PostgreSQL is the target database engine.
- Database objects must use explicit `snake_case` names.
- Technical identifiers must remain `BIGINT` unless a new migration and model
  change explicitly justify another type.
- Structured JSON fields must use PostgreSQL `JSONB`.
- Timestamp fields must use `TIMESTAMP`.
- The reference structure is described in the `Schema Definition` section below.
  Update it whenever a schema change adds, removes, renames or changes a table,
  column, sequence, constraint or relation.
- For database models, keep one ORM class and one source file per model.
- Keep SQL repositories responsible for persistence details and keep business
  decisions in backend services.

## Schema Definition

### Tables

#### `t_schema_version`

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `version` | `VARCHAR(5)` | No | Application version stored after schema initialization. |
| `date_creation` | `TIMESTAMP` | No | First schema creation date. |
| `update_date` | `TIMESTAMP` | Yes | Last application version update date. |

Constraints:

- Primary key: `version`

#### `t_platform`

| Column | Type | Null | Description |
| --- | --- | --- | --- |

| `name` | `VARCHAR(64)` | No | Platform name. |
| `release_date` | `TIMESTAMP` | Yes | Platform release date. |
| `manufacturer` | `VARCHAR(128)` | Yes | Platform manufacturer. |
| `description` | `JSONB` | Yes | Structured platform description. |
| `status` | `VARCHAR(16)` | No | Functional platform status. |

Constraints:

- Primary key: `id`

#### `t_studio`

#### `t_game`

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | No | Technical identifier generated by `s_game`. |
| `name` | `VARCHAR(256)` | No | Game name. |
| `release_date` | `TIMESTAMP` | Yes | Game release date. |
| `developer` | `BIGINT` | Yes | Game development studio. |
| `editor` | `BIGINT` | Yes | Game publishing studio. |
| `platform` | `BIGINT` | No | Game platform. |
| `description` | `JSONB` | Yes | Structured game description. |

Constraints:

- Primary key: `id`
- Unique key: `name`, `platform`
- Foreign key: `developer` -> `t_studio.id`
- Foreign key: `editor` -> `t_studio.id`
- Foreign key: `platform` -> `t_platform.id`

Indexes:

- `ix_t_game_platform`: `platform`
- `ix_t_game_developer`: `developer`

#### `t_user`

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `id` | `BIGINT` | No | Technical identifier generated by `s_user`. |
| `email` | `VARCHAR(256)` | No | User email address. |
| `password_hash` | `VARCHAR(512)` | No | Non-reversible password hash. |
| `profile` | `VARCHAR(16)` | No | Application profile, either `USER` or `ADMIN`. |
| `status` | `VARCHAR(32)` | No | Functional user status, either `ACTIVE`, `WAITING_VALIDATION` or `LOCKED`. |
| `is_email_verified` | `BOOLEAN` | No | Indicates whether the email address has been verified. |
| `email_verification_token_hash` | `VARCHAR(64)` | Yes | SHA-256 hash of the email verification token. |
| `email_verification_expires_at` | `TIMESTAMP` | Yes | Email verification token expiration date. |
| `email_verified_at` | `TIMESTAMP` | Yes | Email verification date. |
| `creation_date` | `TIMESTAMP` | No | User creation date. |
| `last_connexion_date` | `TIMESTAMP` | Yes | Last sign-in date. |
| `collection_file_path` | `VARCHAR(512)` | Yes | Attached collection file path. |
| `collection_file_description` | `JSONB` | Yes | Structured collection file description. |

Constraints:

- Primary key: `id`
- Unique key: `email`
- Check: `profile` in `USER`, `ADMIN`
- Check: `status` in `ACTIVE`, `WAITING_VALIDATION`, `LOCKED`

`collection_file_path` is set by the user collection import workflow only after
a successful import. It stores the complete container path
`/users/workspace/<user_id>/<user_id>-collection.ods`. A non-null value means the
user already has an imported collection and a second import must be rejected
instead of replacing existing data.

#### `t_user_collection`

| Column | Type | Null | Description |
| --- | --- | --- | --- |
| `user_id` | `BIGINT` | No | User who owns the collection entry. |
| `game_id` | `BIGINT` | No | Game attached to the user. |
| `game_additional_name` | `VARCHAR(256)` | Yes | Additional game name in the user collection. |
| `wishlist` | `BOOLEAN` | No | Indicates whether the attached game is a wishlist entry instead of an owned collection entry. |

Constraints:

- Primary key: `user_id`, `game_id`
- Foreign key: `user_id` -> `t_user.id`
- Foreign key: `game_id` -> `t_game.id`

Indexes:

- `ix_t_user_collection_game_id`: `game_id`

Rows are created by the user collection import workflow for every imported game
attached to the connected user. Existing `(user_id, game_id)` rows are reused and
must not be treated as errors. `game_additional_name` remains nullable and is not
filled by the current import workflow. `wishlist` defaults to `false`; existing
rows are backfilled to `false` by the schema migration.

### Import Normalization Rules

The user collection import workflow compares platform, studio and game names
with a normalized key: trim whitespace, lowercase the value, then remove accents
with Unicode normalization. The stored value preserves accents after trimming and
lowercasing.

During import:

- platforms are matched by normalized `t_platform.name`;
- studios are matched by normalized `t_studio.name`;
- games are matched by normalized `t_game.name` and platform;
- duplicate rows in the ODS file are ignored after the first normalized match;
- invalid or empty game release dates are stored as `NULL`.

## Migration Rules

- Use Alembic migrations for every database structure change.
- Never rely on manual SQL execution as the normal deployment path.
- New migrations must be forward-only fixes for production data: they must not
  require emptying, recreating or resetting a production database.
- Prefer idempotent SQL for corrective migrations when rerun safety is useful,
  for example `ADD COLUMN IF NOT EXISTS` or `DROP COLUMN IF EXISTS`.
- When adding a non-nullable column to a table that may contain data, provide a
  safe transition plan: nullable column, backfill, then constraint tightening
  when needed.
- Preserve existing data when renaming or splitting columns; use explicit data
  migration SQL rather than dropping and recreating data.
- Schema initialization and Alembic orchestration changes belong in
  `backend/migrations/env.py` or database infrastructure services, not in
  released migration scripts.

## Released Migration Immutability

Release tags matching `X.Y.Z` are production boundaries. A migration script under
`backend/migrations/versions/` that exists in any released tag must be treated as
immutable.

- Before editing an existing migration, check released tags with
  `git tag --list` and compare the migration against released tags.
- Do not modify a released migration's content, revision metadata, signature or
  behavior.
- If a released migration is wrong or incomplete, create a new migration that
  corrects the live database state.
- Never propose deleting Docker volumes, dropping production schemas, truncating
  production tables or resetting the production database as the normal fix for a
  migration issue.
- Local database resets are acceptable only for local test data, and they must
  be explicitly described as local-only.

## Validation

When modifying database structure, ORM models, SQL repositories, schema
initialization or migrations:

- update or add backend tests covering the changed persistence behavior;
- run `./test_backend.sh`;
- rebuild affected Docker images when runtime behavior changes;
- update this document's `Schema Definition` section for every schema change;
- verify whether `README.md`, `documentation/ci.md` or another functional
  document must be updated;
- verify local Docker startup when the change affects schema initialization or
  migrations.
